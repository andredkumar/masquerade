# Phase 5C-1 — RDS Provisioning & Conformance Runbook

**Audience:** Andre (operator). **Executed by you, not the agent** — every step
below touches AWS resources and secrets you control. Nothing here is automated by
the codebase and no secret is committed to the repo.

**Decision B = B1 (RDS, managed Postgres).** This runbook stands up a *disposable
test database*, applies the `0000` baseline migration, and runs the `IStorage`
conformance harness (`MemStorage` oracle vs. `PgStorage`). It does **not** change
anything the live app reads — `MemStorage` remains the runtime (`server/storage.ts`
ends with `export const storage = new MemStorage()`). PgStorage is wired to nothing
live; this is foundation validation only.

> **Scope guard:** 5C-1 provisions infrastructure for *testing* and proves the
> storage layer is swappable. The production cutover (pointing the app at Postgres)
> is **5C-2** — out of scope here.

---

## 0. Prerequisites

- AWS account access with permission to create an RDS instance + security group.
- The app EC2 instance's VPC / security-group IDs (so the DB can be reached from
  the app host, and from wherever you run the harness).
- Local toolchain: Node (the repo's `tsx`/`drizzle-kit` are already in
  `devDependencies`), `psql` for the manual down-path.

---

## 1. Environment variables (you set these; never commit them)

| Var | Used by | Purpose | Notes |
|-----|---------|---------|-------|
| `DATABASE_URL` | `server/db.ts`, `drizzle.config.ts`, `npm run db:migrate` | App-instance connectivity + the migration target | Already referenced by the code. `db.ts` **throws at boot if unset.** |
| `TEST_DATABASE_URL` | `scripts/conformance-storage.ts` | Test-only DB the harness truncates between cases | **New in 5C-1.** Point ONLY at a disposable DB — the harness runs `TRUNCATE`. |

Format (both): `postgresql://USER:PASSWORD@HOST:5432/DBNAME`

**SSL is gated in code (one shared resolver), not in the URL.** `server/dbSsl.ts`
enables SSL (`rejectUnauthorized: false`, a disposable-test-DB choice) automatically
when the host **contains `rds.amazonaws.com`** **or** the URL carries an explicit
`sslmode` (other than `disable`). Both connection paths import it — `server/db.ts`
(the harness Pool) **and** `drizzle.config.ts` (the `db:migrate` connection) — so
migrate and harness make the identical SSL decision. So the plain
`postgresql://…@HOST:5432/DBNAME` form above works as-is against RDS for **both**
`db:migrate` and the harness — you do **not** need to append `?sslmode=` for it. (The
`psql` probe in step 3.5 is a separate client and may need its own `?sslmode=require`;
see that step.) A plain local/dev Postgres (non-RDS host, no `sslmode`) stays SSL-off
and unchanged.

`.env.example` documents `DATABASE_URL`. Add `TEST_DATABASE_URL` to your local
`.env` (not tracked) when running the harness. **Do not** put either real value in
`.env.example` or any committed file.

## 2. Provision the RDS instance (managed Postgres)

Use the console or CLI; the shape that matters:

- **Engine:** PostgreSQL (15+; the schema uses `gen_random_uuid()`, built into
  pgcrypto/PG13+ — no extension step needed on modern PG).
- **Encryption at rest:** **ON** (KMS). This is a primary reason B1 was chosen —
  required posture for the PHI that lands later.
- **Backups:** automated snapshots + PITR (RDS default) — leave enabled.
- **Network:** private subnet; security group allows `5432` inbound **only** from
  the app EC2 security group (and, temporarily, from wherever you run the harness).
- **Credentials:** strong generated password; store in your secrets manager, not
  the repo.
- For the **test** database, either a separate small instance or a separate
  database/schema on the same instance — as long as `TEST_DATABASE_URL` resolves to
  something you are willing to `TRUNCATE`.

> The agent did **not** create any of this. Provisioning, credentials, and KMS are
> yours to control.

## 3. Apply the baseline migration

The versioned migration lives at `migrations/0000_hard_cable.sql` (generated by
`drizzle-kit generate`; forward-only). Under **A3** it creates **three** tables —
`jobs` (28 columns; the single source of truth, no `video_job` blob and no
`has_job_v2`), `ai_runs` (FK → `jobs.id` `ON DELETE cascade`), and
`frame_processing_batches` (FK → `jobs.id`). There is **no** `video_jobs` table:
the legacy `VideoJob` shape is derived from columns on `jobs` by the PgStorage shim.

Apply it with the drizzle migrator:

```bash
cd masquerade-aws-latest
DATABASE_URL="$TEST_DATABASE_URL" npm run db:migrate
```

(`db:migrate` runs `drizzle-kit migrate`, which reads `drizzle.config.ts` →
`out: "./migrations"` and applies pending versioned migrations, recording them in
the `__drizzle_migrations` bookkeeping table.)

Repeat against the **production** DB later (5C-2), pointing `DATABASE_URL` at it —
not part of 5C-1.

## 3.5 Prove the connection before testing logic

Run a reachability + SSL handshake probe **after** the migration (step 3) and
**before** the harness (step 4). This isolates a connection/SSL problem from a real
A3 assertion failure, so you never debug infra thinking it is a schema bug.

```bash
# Plain reachability + SSL handshake check
psql "$TEST_DATABASE_URL" -c "SELECT 1;"
```

Read the result:

- **Returns `1`** → connection path is clean (network + SSL + credentials all good).
  Proceed to step 4; any harness failure now is a **real assertion failure** worth
  investigating as an A3 derivation issue.
- **Hangs / times out** → **security group.** Your workstation's current public IP
  isn't allowed inbound on `5432`. Add the temporary ingress rule (your *current*
  public IP/32; update it if your network rotates IPs). Not a schema problem.
- **SSL error** (e.g. `no pg_hba.conf entry … no encryption`, or a TLS/cert error)
  → for the `psql` probe specifically, append `?sslmode=require` to the URL:
  ```bash
  psql "$TEST_DATABASE_URL?sslmode=require" -c "SELECT 1;"
  ```
  Both `db:migrate` and the harness use the shared `dbSsl.ts` SSL config (which
  auto-enables SSL for any host containing `rds.amazonaws.com` — see step 1), **not**
  `psql`'s; this `sslmode` is only for the probe. If the probe needs it, that confirms
  the RDS host is reached.
- **Auth error** (`password authentication failed`) → credentials in
  `TEST_DATABASE_URL` are wrong. Config, not schema.

Then confirm the migration actually created the three tables before running the
harness (catches a silent partial migrate):

```bash
psql "$TEST_DATABASE_URL" -c "\dt"
```

Expected: `jobs`, `ai_runs`, `frame_processing_batches` (plus the
`__drizzle_migrations` bookkeeping table). **No** `video_jobs` (A3 has none). If
`gen_random_uuid()` errored during migrate with "function does not exist," run
`CREATE EXTENSION IF NOT EXISTS pgcrypto;` then re-run `db:migrate` — unlikely on
PG15, but that is the remedy.

## 4. Run the conformance harness

```bash
cd masquerade-aws-latest
TEST_DATABASE_URL="postgresql://…disposable…" npx tsx scripts/conformance-storage.ts
```

- With `TEST_DATABASE_URL` **set**, the harness runs the full suite against **both**
  `MemStorage` and `PgStorage` and asserts identical behavior.
- With it **unset**, only `MemStorage` runs (useful as a quick oracle sanity check;
  this is what CI/the agent can run without a DB).

**Expected output (both backends):**

```
  MemStorage: 35/35 cases ran, PASS
  PgStorage:  35/35 cases ran, PASS

… assertions across 2 backend(s).
ALL SUITES PASSED
```

Exit code `0` = pass, `1` = any failure or setup error. If PgStorage setup fails,
the harness prints a hint to confirm the DB is reachable and migrated (step 3).

**What the suite proves** (all 21 `IStorage` methods):
- VideoJob create/get/update round-trips faithfully (derived from `jobs` columns).
- Dual-facet: the `VideoJob` and `Job` facets share **one** `jobs` row and are
  **independent** (deleting one facet clears only its exclusive columns + status
  marker, leaving the other facet — including the shared columns — intact).
- Status mirror: `updateVideoJob('ready'|'completed'|'failed')` ⇒
  `getJobV2().status` mirrors via `mapVideoJobStatusToJobStatus`, **only when the
  Job facet exists**; an unmapped status is a no-op.
- AI lifecycle: `addAiRun` → `listAiRuns` (insertion order) → `getAiRun` →
  `updateAiRun` → `deleteAiRun`; `ai.runs` stays **present-but-empty** after the
  last run is deleted (the `ai_initialized` marker).
- Cascade: `deleteJobV2` removes the job's `ai_runs`.

## 5. Rollback (drop the baseline)

The baseline is reversible via the hand-authored down-path (drizzle `generate` is
forward-only, so this file is maintained by hand):

```bash
cd masquerade-aws-latest
psql "$TEST_DATABASE_URL" -f migrations/down/0000_hard_cable.down.sql
```

It drops `frame_processing_batches`, `ai_runs`, `jobs` in reverse dependency order. On a fresh test DB there is no data to lose. (You will also want
to clear the `__drizzle_migrations` row if you intend to re-apply `db:migrate`
cleanly afterward.)

For the whole experiment, the lowest-risk rollback is simply **deleting the
disposable RDS instance** — nothing live depends on it.

## 6. After a green run

Report the harness output (the `ALL SUITES PASSED` block) back so it can be
recorded in `PHASE_5C1_REPORT.md` under "Conformance results vs. RDS." Then:

- **Tear down** the temporary harness ingress (the security-group rule that let
  your workstation reach `5432`), leaving only app-EC2 → DB.
- Keep `TEST_DATABASE_URL` out of any committed file.
- 5C-1 ends here. The production cutover (app reads Postgres, dual-write/backfill,
  flip `storage.ts` to `PgStorage`) is **5C-2**. Under A3 there is no `video_jobs`
  table to retire — `jobs` is already the sole job-bearing table.
